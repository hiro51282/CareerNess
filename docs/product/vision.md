# Vision

CareerNess は、キャリア情報を「都度書き直す文章」ではなく、「再利用可能な構造化データ」として扱うための Local-first プラットフォームである。

転職活動やキャリア発信では、同じ経歴でも用途ごとに見せ方を変える必要がある。職務経歴書、スカウト返信、面接用要約、role 別プロフィールはそれぞれ求める粒度や強調点が異なる。しかし、元になる事実が文章の中に埋まっていると、毎回編集し直すことになり、情報の欠落や誇張、表現のゆがみが起こりやすい。

CareerNess が解決したいのは、この「キャリアの事実」と「見せ方」が混ざっている状態である。目指すのは、ユーザー自身のキャリアを掘り起こし、構造化し、必要に応じて複数のプロフィールや export に変換できる状態を作ることだ。

## なぜ存在するのか

CareerNess は、AI に経歴を丸投げするためのプロダクトではない。ユーザーが自分のキャリアの正本を持ち、その正本をもとに AI の支援を受けながら見せ方を調整できるようにするために存在する。

重要なのは、次の順序を守ることである。

1. 事実を集める
2. 構造として整理する
3. 文脈に応じたプロフィールへ変換する
4. export する

この順序が崩れると、AI はもっともらしい文章を作れてしまう一方で、ユーザーの実際の経験から離れやすくなる。

## 目指す体験

CareerNess が目指す体験は、派手な自動生成ではなく、次のような地に足のついた作業支援である。

- ユーザーが workspace を attach すると、その範囲だけで AI と対話できる
- AI は過去のプロジェクト、役割、成果を質問しながら facts を抽出する
- facts は人間が読める形で workspace に保存される
- profile は facts を元に用途別に生成・調整される
- export は profile から作られる派生物として扱われる

この体験の中心は「一度きりの出力」ではなく、「後から見直し、修正し、再利用できるキャリア資産」を作ることである。

## Local-first を採用する理由

CareerNess で扱う情報は、職歴、役割、評価、転職意向、自己認識など、個人に強く紐づくデータである。この種の情報は、単に秘匿性が高いだけではなく、「誰が正本を持つか」が重要である。

CareerNess が Local-first を重視する理由は次の通り。

- キャリア情報の ownership をユーザー側に置きたい
- 運営側が巨大な個人データ保管庫になることを避けたい
- AI を使うために、常にクラウドへデータを集約する前提を持ち込みたくない
- ユーザーが markdown や構造化ファイルとして自分の情報を直接確認できるようにしたい

Local-first は「すべてをローカルで閉じる」という思想ではない。AI 機能や認証のためにネットワーク経由の要素はありうる。ただし、その場合でもキャリアの正本は workspace に置き、クラウド側はできるだけ薄く保つのが基本方針である。

## 設計上の前提

- CareerNess の正本は profile ではなく facts である
- profile は見せ方の単位であり、正本ではない
- export は提出・共有のための派生物である
- AI は所有者ではなく支援者である
- AI が触れてよい範囲は attach 済み workspace に限定される
- 未確定の将来要件を見越して巨大な基盤を先に作らない

## 未確定事項

- embeddings directory を MVP で持つかどうかは未確定
